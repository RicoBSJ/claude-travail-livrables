# 2026-09-25_lecon-appli-ia_09_qualite-tests-debogage

Document source : [[2026-09-25_lecon-appli-ia_09_qualite-tests-debogage.docx]]

## Résumé

**Tout ce que la leçon présente comme mesuré est exact, et l'incrément fonctionne : c'est la leçon du parcours dont les chiffres tiennent le mieux.** Les cinq fichiers sont sur le disque, datés du matin (`filtres.ts` 08:07:19, `App.tsx` 08:07:32, `tests.js` 08:08:09, `tests-filtres.mts` 08:09:19, `package.json` 08:09:35), et le commit `0e990b2` les porte (+457/−82 sur douze fichiers). J'ai tout rejoué : `node scripts/tests.js` rend **17 tests · 3 suites · 17 pass · 0 fail** en **16,6 ms** à chaud — le « ~15 ms » annoncé est une mesure, pas une estimation ; `node --test scripts/tests-filtres.mts` rend **16 tests · 2 suites** ; `npm test` enchaîne les deux et donne bien **33 · 5 suites · 0 fail**, avec la précision honnête « (17 + 16) » puisque la commande n'imprime jamais de total unique. Le code de sortie **1 sur échec** est vérifié. Le cas limite `veille-essms-2026-05-20-2026-05-26.fiche.md → null` est dans le fichier et passe, et c'est le seul test que l'IA ne pouvait pas inventer — la leçon le dit et le prouve. Les deux questions du Challenge ont une réponse observable : `extraireDate('rapport_2026-13-45.docx')` rend **`'2026-13-45'`** (le regex ne valide pas le calendrier) et `matcheFiltres(…, ' ', '')` rend **`true`**, parce que `cible` est `nom + ' ' + slug` et contient donc toujours une espace ; la promesse « 35 tests · 0 fail » est atteignable. La continuité est exacte au mot : `App.tsx` au commit `2175296` portait bien, ligne 34, *« Exportée ici pour être réutilisable et testable unitairement en leçon 09 »* — l'engagement pris la semaine dernière est tenu. Le déplacement ne casse rien : `npx tsc --noEmit` **exit 0**, `vite build` **✓ 20 modules transformed**, dépôt propre. Côté sources, *« Stability: 2 - Stable »* est bien sur `nodejs.org/api/test.html` (la leçon met un tiret cadratin là où la page met un trait d'union), *« Added in: v18.0.0 »* valide « depuis Node.js v18 », et `previous-releases` affiche **v24.21.0 Latest LTS**. Contrôles : `controle_attributions` **exit 0**, deux B-FR « à relire » qui sont les propres formules de la leçon ; `controle_decompte` **inerte** (aucune rubrique Sources à symboles).

**Le défaut central est une famille neuve dans ce parcours : quatre chaînes présentées comme la sortie littérale d'un outil, que l'outil n'imprime pas.** Le plus grave est l'exercice 3, parce que c'est l'exercice d'apprentissage de la leçon — on casse un test pour apprendre à lire l'échec. La leçon publie `AssertionError [ERR_ASSERTION]: '2026-04-06' == '2099-01-01'` puis commente : *« C'est le format AssertionError de `node:assert/strict` »*. J'ai rejoué le sabotage exactement comme prescrit, sur une copie : le vrai message est **`Expected values to be strictly equal:`** — la forme `X == Y` est celle de l'`assert.equal` *legacy* (Stability 3 sur la page que la leçon cite). Trois erreurs de plus dans le même bloc de six lignes : la trace dit `scripts/tests.js:43:12` alors que l'`assert.strictEqual` est **ligne 46** (le `test(` est ligne 45) ; l'**ordre est inversé**, le vrai `node:test` imprime le diff `+ actual - expected` **avant** la pile, la leçon met la pile d'abord ; et il manque la ligne du caret `^` que Node ajoute sous le diff. Un débutant qui compare son écran à la leçon ne reconnaît rien. Deux lignes du tableau des erreurs fréquentes sont du même tissu. `Error: No test files found` : lancé sans chemin, `node --test` imprime `ℹ tests 0 … pass 0 fail 0` et **sort en 0** — la chaîne n'existe nulle part dans la sortie. Et la ligne `Cannot find module './utils'` est **fausse dans sa cause et dans son remède** : elle dit que l'erreur vient d'un mauvais répertoire de lancement et prescrit *« Lance depuis la racine du projet : `node scripts/tests.js` (pas depuis `scripts/`) »*. Mesuré : depuis `scripts/`, **17/17 passent** ; depuis `/tmp` avec un chemin absolu, **17/17 passent** — `require('./utils')` se résout relativement au **fichier** (`__dirname`), jamais au `cwd`. La leçon enseigne l'inverse d'une règle fondamentale de CommonJS, dans une leçon dont le sujet est de savoir lire une erreur.

**Le drapeau `--experimental-strip-types` est inutile, retiré de la documentation depuis trois versions de Node, et il figure quatre fois dans la livraison.** Il est dans l'annonce de l'incrément, dans la commande de l'étape 4, dans l'explication (*« Le flag `--experimental-strip-types` retire les annotations TypeScript à la volée »*) et jusque dans l'en-tête de `filtres.ts`, qui justifie l'existence du module par lui. Mesuré dans les deux sens et sur les deux binaires de la machine : `node --test scripts/tests-filtres.mts` **sans le drapeau** rend 16 pass, sur v24.15.0 comme sur v24.18.1, sans un avertissement. La page officielle `nodejs.org/api/cli.html` — page sœur des deux que la leçon cite — porte l'historique dans sa table `--no-strip-types` : *« v23.6.0, v22.18.0 — Type stripping is enabled by default »* et *« v25.2.0, v24.12.0 — Type stripping is now stable, the flag was renamed from `--no-experimental-strip-types` to `--no-strip-types` »*. Le projet tourne sur **v24.15.0**, soit trois correctifs après le renommage. La forme non niée `--experimental-strip-types` apparaît **0 fois** dans la documentation courante ; elle survit comme alias dans `node --help`, c'est tout. C'est le garde-fou nominal du parcours qui saute — *« ne jamais écrire de version de bibliothèque ni de signature d'API de mémoire (écosystème très mouvant) → vérifier à la doc officielle »* : le drapeau a été écrit de mémoire, à un moment où il était juste. En revanche la **décision** qu'il justifie est solide et vérifiée : Node refuse un `.tsx` avec `ERR_UNKNOWN_FILE_EXTENSION` (testé sur `App.tsx`) et échoue à parser du JSX dans un `.mts`, donc extraire `matcheFiltres` vers `filtres.ts` était nécessaire. Bon geste, mauvaise justification — la forme exacte du garde-fou 2 du 09/08 et du défaut Vite du 18/09. Et la mesure de version est, elle, honnête : `/usr/local/bin/node` (celui du launchd) **est** en v24.15.0 ; un lecteur dans son terminal obtient v24.18.1 par nvm. Deux binaires, deux mesures justes.

**Le second extrait de code de la théorie ne tourne pas, et c'est celui que la leçon présente comme équivalent au premier.** Le bloc « Deux syntaxes coexistent — elles font la même chose » importe `{ test }` seul, puis emploie `describe` et `it`. Copié tel quel : **`ReferenceError: describe is not defined`**, exit 1 — les deux alias doivent être importés de `node:test`, il n'y a pas d'injection globale. Le fichier livré, lui, fait juste (`const { test, describe } = require('node:test')`), donc le défaut est confiné à l'extrait pédagogique — mais c'est l'extrait que le lecteur copie. À l'inverse, deux durcissements du 18/09 **ont tenu**, et il faut le dire : l'étape 6 a produit exactement ce qu'on lui demandait, `PROJET.md` porte *« non traité en leçon 09 — reporté le 25/09/2026 en leçon 11 (mise en production) »* avec son motif, au lieu de l'effacement silencieux de la semaine dernière ; et la règle (e) est satisfaite sans détour, chaque sortie de commande étant écrite « Sortie mesurée le 25/09/2026 : … » — et à chaque fois vraie. Reste que **l'étape 5 bis rend `OK` et sort en 0** sur ce document : XML conforme, 2 tableaux, 3 liens, 27 puces dont 0 vide, « observations et comportements datés ». Elle ne pouvait pas voir ces quatre défauts : (e) traque les phrases « tu dois voir / vérifie que … apparaît », que la leçon n'emploie jamais, et (f) traque un comportement *nié* prêté à un outil nommé — or `« il ne gère pas le JSX »` échappe à sa liste de négations, et un message d'erreur recopié dans une cellule de tableau n'est ni l'un ni l'autre. Le contrôle manquant est d'une autre nature : **toute chaîne présentée comme la sortie littérale d'un outil — nom d'exception, trace, message entre guillemets ou en bloc de code — doit avoir été produite pendant l'exécution.** C'est mécanisable, et ça vaut pour les cinq parcours, pas seulement celui-ci.

**Le coût atteint 90 % du plafond, et la vérification n'a pas suivi la dépense.** **2,7036 $ pour un plafond de 3,00 $**, **71 tours**, 12 min 02 s, out 44 199 tokens, **5 321 282 tokens de cache lu** : la course la plus chère du parcours (+29 % sur la leçon 08 à 2,10 $, +66 % sur la 07 à 1,63 $) et, à 90 %, la plus proche de son plafond de tous les jobs relevés — la semaine prochaine touche le mur. Les tours passent de 44 à **71** (+61 %) et le prompt de 64 372 à **74 610 octets**, relu à chaque tour. Deux tiers de tours en plus ont servi à écrire un incrément juste et des mesures exactes, pas à lancer les six commandes qui auraient dégonflé cette fiche : rejouer le sabotage de l'exercice 3 (30 s), lancer `node --test` sans chemin (2 s), lancer `node tests.js` depuis `scripts/` (2 s), retirer le drapeau (2 s), copier l'extrait de syntaxe 2 (5 s). C'est le deuxième document d'affilée dont le **tableau des erreurs fréquentes** porte une ligne inventée — la leçon 08 attribuait `db.prepare is not a function` à une cause fausse avec un remède sans objet, la 09 en porte deux — et c'est la troisième fois dans le parcours qu'une sortie publiée ne correspond pas à ce que l'outil imprime (leçon 03, leçon 08, celle-ci). Ce que la leçon réussit mérite d'être noté : la section « ce que l'IA fait mal sur les tests » est juste et utile, et sa règle finale — *« si cette fonction était cassée de la pire façon possible, est-ce que ce test le détecterait ? »* — est exactement la question que le tableau des erreurs de la même leçon n'a pas posée à ses propres lignes.
